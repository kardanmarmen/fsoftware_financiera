# 1.1 Análisis de requisitos de acceso

**Incremento 1:** Gestión de usuarios, roles y seguridad
**Responsable:** Martínez Mendoza Karlo Daniel
**Documento base:** Requisitos del sistema de una financiera (Unidad 1)

## 1. Objetivo

Definir quién puede entrar al sistema, cómo se identifica, qué puede hacer cada rol y qué reglas
controlan las sesiones y las contraseñas. Este análisis es la base del diseño (1.2) y de las
funciones de registro de usuarios (1.3), inicio de sesión (1.4) y recuperación de contraseña (1.5).

## 2. Actores

| Actor | Descripción | Quién lo da de alta |
| --- | --- | --- |
| **Administrador** | Administración técnica del sistema. Consulta la información, pero no interviene en las operaciones financieras. | Script de instalación (primer arranque) |
| **Gerente** | Supervisa a sus Cobradores, aprueba solicitudes y autoriza operaciones críticas. | Administrador |
| **Cobrador** | Atiende a los clientes y registra solicitudes, pagos y abonos. Pertenece a un solo Gerente. | Gerente o Administrador |

No existe registro público: ninguna persona puede crear su propia cuenta.

### 3.2 Requisitos no funcionales

| ID | Requisito | Cómo se cumple |
| --- | --- | --- |
| RNF14 | Comunicación cifrada | Todo el tráfico va por HTTPS. |

## 4. Reglas de negocio

### Usuarios

| ID | Regla |
| --- | --- |
| RN-01 | El nombre de usuario es único, de 3 a 30 caracteres, y solo admite letras minúsculas, números, punto, guion y guion bajo. Se guarda en minúsculas: `JPerez` y `jperez` son el mismo usuario. |
| RN-02 | Todo Cobrador pertenece a exactamente un Gerente activo. Gerentes y Administradores no tienen Gerente. |
| RN-03 | El Gerente solo puede crear, editar, activar o desactivar Cobradores que le pertenecen. |
| RN-04 | Solo el Administrador puede reasignar un Cobrador a otro Gerente. El Cobrador conserva sus clientes. |
| RN-05 | No se puede desactivar a un Gerente mientras tenga Cobradores activos: primero deben reasignarse. |
| RN-06 | Al desactivar a un usuario se cierran todas sus sesiones abiertas. |
| RN-07 | Un usuario no puede desactivarse a sí mismo. |
| RN-08 | Los usuarios no se eliminan; se desactivan, para conservar el historial de sus operaciones. |
| RN-09 | El rol de un usuario no cambia después de creado. |

### Contraseñas

| ID | Regla |
| --- | --- |
| RN-10 | La contraseña tiene entre 8 y 128 caracteres. |
| RN-11 | Solo el Administrador puede restablecer contraseñas. El sistema genera una contraseña temporal y la muestra **una sola vez** al Administrador. |
| RN-12 | La contraseña temporal caduca a las **24 horas**. Si caduca, el Administrador debe generar otra. |
| RN-13 | Quien entra con contraseña temporal solo puede cambiar su contraseña; no puede usar ninguna otra función hasta hacerlo. La nueva debe ser distinta a la temporal. |
| RN-14 | Al restablecer una contraseña se cierran las sesiones abiertas del usuario. |
| RN-15 | Cualquier usuario puede cambiar su propia contraseña escribiendo la actual. |

### Sesiones

| ID | Regla |
| --- | --- |
| RN-16 | Una cuenta tiene como máximo una sesión abierta. Iniciar sesión cierra la anterior. |
| RN-17 | Una sesión es válida solo si: el usuario está activo, la sesión no fue cerrada, tuvo actividad en los últimos 3 días y se creó después del último cierre dominical. |
| RN-18 | El cierre dominical ocurre cada domingo a las 03:00, hora del centro de México (UTC−6, sin horario de verano). |
| RN-19 | La última actividad de la sesión se actualiza como máximo una vez cada 15 minutos. |

## 5. Eventos que registra la bitácora

| Evento | Quién lo genera |
| --- | --- |
| Inicio de sesión exitoso | Cualquier usuario |
| Intento de inicio de sesión fallido | Sistema (con el nombre de usuario intentado) |
| Cierre de sesión | Cualquier usuario |
| Alta de usuario | Administrador o Gerente |
| Modificación de usuario | Administrador o Gerente |
| Activación o desactivación | Administrador o Gerente |
| Reasignación de Cobrador | Administrador |
| Restablecimiento de contraseña | Administrador |
| Cambio de contraseña | El propio usuario |

**Quién consulta la bitácora:** el Administrador ve todos los registros; el Gerente, solo los suyos
y los de sus Cobradores (RF-122); el Cobrador no tiene acceso.

## 6. Decisiones del equipo

| Tema | Decisión |
| --- | --- |
| Identificación | Nombre de usuario, no correo electrónico. |
| Recuperación de contraseña | Contraseña temporal asignada por el Administrador; sin envío de correos. |
| Alta de Cobradores | La hacen el Gerente y también el Administrador. |
| Restablecer contraseñas | Solo el Administrador. |
| Hora del cierre dominical | Domingo 03:00 (horario de menor actividad, no interrumpe la cobranza del sábado por la noche). |
| Caducidad de la contraseña temporal | 24 horas. |
| Gerente con Cobradores activos | No se puede desactivar hasta reasignarlos. |
| Intentos de inicio de sesión | Máximo 5 por minuto por IP y usuario; al pasarse, se pide esperar un minuto. No se bloquea la cuenta. Los intentos fallidos quedan en bitácora. |
| Costo de scrypt | 1024 (verificar una contraseña tarda ~3 ms), para no exceder el límite de CPU del plan gratuito de Cloudflare. El límite de intentos compensa la reducción. |
| Pepper | Antes de scrypt, la contraseña se firma con HMAC-SHA256 y una clave secreta guardada en Cloudflare (no en la base). Si se roba solo la base, los hashes no sirven para adivinar contraseñas. Los scripts de administración crean contraseñas temporales sin pepper, y el sistema se lo agrega en el primer inicio de sesión. |

## 7. Supuestos

Puntos que el documento base no define y que se resolvieron así; pueden cambiarse si el equipo lo decide:

- El primer Administrador se crea con un script de instalación. No hay pantalla para crear Administradores.
- El rol no cambia después de crear al usuario (RN-09). Si alguien cambia de puesto, se le crea una cuenta nueva.
- Un Administrador no puede desactivarse a sí mismo (RN-07), para evitar quedarse sin acceso.
- "Actualizar la información" de un usuario (RF25, RF30) incluye su **nombre completo** y su
  **nombre de usuario**. Los cambia su superior: el Gerente a sus Cobradores, el Administrador a
  Gerentes y Cobradores. El historial no se pierde, porque la bitácora usa el identificador interno
  y guarda el valor anterior y el nuevo.
- Nadie modifica sus propios datos, porque los controla su superior (RF25, RF30). **Excepción:** el
  Administrador corrige su propio nombre desde "Mi cuenta", ya que no tiene superior y ningún
  requisito indica quién administra su cuenta. Su rol, estado y nombre de usuario no se pueden cambiar.
- Todos los usuarios pueden consultar los datos de su cuenta en "Mi cuenta" y cambiar su contraseña.
- Si un Administrador olvida su contraseña, se restablece con el script `restablecer-admin`, porque
  desde el sistema nadie puede restablecer la de un Administrador (RF08 solo cubre Gerentes y Cobradores).

## 8. Fuera del alcance de este incremento

- Recuperación de contraseña por correo o SMS (fuera del alcance del proyecto, punto 9).
- Bloqueo permanente de la cuenta por intentos fallidos (solo se limita la velocidad de los intentos).
- Códigos de autorización del Gerente para operaciones críticas (RF33, RF106–RF108): se implementan
  junto con las operaciones que los requieren.
- Transferencia de clientes y créditos entre Cobradores (RF16, RF29): incremento de clientes y créditos.
