# 6.6 Implementación en producción

**Incremento 6:** Integración, pruebas finales e implementación
**Requisitos:** RNF01, RNF02, RNF03, RNF11, RNF14, RNF23

Pasos para publicar los Incrementos 3 a 5 en Cloudflare. Los hace alguien con acceso a la cuenta
(`npx wrangler login`). **El orden importa: primero la base de datos y el almacenamiento, después la
aplicación.** Si la aplicación nueva corre sin las migraciones, fallan las pantallas de créditos,
cobranza y la pantalla de inicio (la tabla `moras` no existe).

## 1. Antes de empezar

```sh
git pull                                    # rama main al día
npm install
npx wrangler d1 time-travel info financiera # anota el "bookmark": punto para regresar si algo sale mal
```

## 2. Almacenamiento de documentos (una sola vez)

```sh
npx wrangler r2 bucket create financiera-documentos
```

El bucket es privado: no se le activa acceso público ni dominio. Los archivos solo salen por la API.

## 3. Migraciones de la base de datos

```sh
npm run db:migrar:remoto
```

Debe aplicar `0006_moras.sql` (tabla `moras` y columna `operaciones.mora_centavos`) y
`0007_documentos.sql` (tabla `documentos`). Ninguna modifica ni borra datos existentes.

## 4. Publicar la aplicación

- **Si el repositorio está conectado a Cloudflare (Workers Builds):** cada push a `main` publica la
  aplicación sola. Revisa en el panel (**Workers → fsoftware-financiera → Deployments**) que el último
  despliegue corresponda al último commit. Si ya se publicó antes de las migraciones, basta con
  aplicarlas (paso 3): las pantallas funcionan en cuanto existen las tablas.
- **Si se publica a mano:**
  ```sh
  npm run build
  npx wrangler deploy
  ```

## 5. Publicar el Worker de respaldos

Cambió para copiar también los documentos (RF118) y ahora usa el bucket de documentos.

Desde el 21/11/2026 se publica solo: en el panel, **Workers & Pages → financiera-respaldos → Settings →
Builds** está conectado al repositorio con rama `main`, *Build command* vacío, *Deploy command*
`npx wrangler deploy` y *Root directory* `/respaldos`. Si alguna vez hay que publicarlo a mano:

```sh
cd respaldos
npx wrangler deploy
```

## 6. Verificación (con usuarios reales, en este orden)

| # | Quién | Prueba | Resultado esperado |
| --- | --- | --- | --- |
| 1 | Administrador | Crear un modelo (por ejemplo "Semanal 16", 20 %, 16 semanas, mora $50, 4 semanas para renovar) | Aparece en **Modelos** |
| 2 | Gerente | En **Mis Cobradores**, asignar modelos a un Cobrador (opcional) | "Modelos guardados" |
| 3 | Cobrador | Capturar una solicitud pequeña para un cliente de prueba y subir una foto | La solicitud aparece pendiente; la foto se abre al tocarla |
| 4 | Gerente | Aprobarla | El crédito queda Aprobado con su calendario |
| 5 | Cobrador | Desembolsar y registrar un pago | Cada paso abre su comprobante |
| 6 | Gerente | Corregir ese pago | El saldo regresa; la corrección tiene su comprobante |
| 7 | Cobrador | Liquidar el crédito | Comprobante de liquidación; el crédito queda Liquidado |
| 8 | Todos | Pantalla de inicio, **Cobranza** y **Reportes** | Cargan sin errores |
| 9 | Administrador | El domingo siguiente (o al disparar el Workflow, ver abajo), en **Respaldos** y **Bitácora** | Respaldo "correcto"; en la bitácora "Respaldo semanal (base de datos y N documentos…)"; en R2 `financiera-respaldos/documentos/<fecha>/` están todos los documentos |

El crédito de prueba se queda en el historial (las operaciones no se borran); conviene usar un cliente
llamado "PRUEBA" para reconocerlo en los reportes.

### Disparar el respaldo sin esperar al domingo

- **Desde el panel:** **Workers & Pages → Workflows → respaldo-semanal → Trigger** (sin parámetros).
  La ejecución muestra cada paso: `guardar en R2`, `copiar documentos (lote 1)`, … y `registrar resultado`.
- **Con una computadora:** `npx wrangler workflows trigger respaldo-semanal`.
- Cada ejecución hace un respaldo real completo (base y documentos) en su propia carpeta con fecha; no
  borra ni modifica los anteriores.

## 7. Si algo sale mal

| Problema | Qué hacer |
| --- | --- |
| Errores en créditos, cobranza o inicio | Revisa que se aplicaron las migraciones (paso 3). |
| No se pueden subir documentos | Revisa que existe el bucket `financiera-documentos` (paso 2) y vuelve a publicar la aplicación. |
| Datos dañados | Regresa la base al punto anotado: `npx wrangler d1 time-travel restore financiera --bookmark=<bookmark>` (ver [2.7](../incremento-2/2.7-respaldo-de-datos.md)). |
| Ver errores y CPU de cada petición | Panel de Cloudflare → Workers → `fsoftware-financiera` → **Observability**. |
